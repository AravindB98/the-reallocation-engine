# Change brief — data-analytics OPT/H-1B role filter

## Executive summary

This brief describes a small addition to the job-search engine. It is for an
international data-analytics graduate about to start post-graduation work
authorization. The addition turns public employer visa-sponsorship records
into a sponsorship score for each job, then passes the job through two hard
stops: is the posting still live, and can the hire happen before the
work-authorization clock runs out. It reuses the existing scorer and liveness
checker, and adds only the missing piece that turns records into scorer
inputs. Every threshold below is a proposal awaiting human review, and the
predictions at the end will be checked against the first real run.

## 1. Career situation

- **Who:** an international MS Data Analytics student graduating Dec 2026 and
  starting F-1 OPT. They target data/analytics roles at companies whose H-1B
  history includes those titles.
- **Target titles (your-input):** Data Scientist, Data Analyst, Machine
  Learning Engineer, Analytics Engineer, Data Engineer, Business Analyst,
  Business Intelligence, Automation Analyst.
- **Prototype persona:** the fictional **Priya Nair**
  (`search/examples/priya-nair/profile.yml`). She is the only F-1/OPT persona
  whose status string does not trip the scorer's sponsorship check
  (`notes/01-repo-findings.md`, Follow-up 4). The real situation above is never
  used as data.
- **Engine layers used:** 80 Days to Stay (sponsorship and funding fields),
  Job-Ops (posting liveness), plus a visa-timeline gate.

## 3. Design decisions

Decided by Nishant; proposed in a chat with Claude. Every threshold is

**Sponsorship tier and p (source: record), from the CSV:**

| Tier | Rule | p |
|---|---|---|
| Proven | title match AND `Total Approvals` ≥ 10 AND `Approval_Rate` ≥ 90 [VERIFY] | 0.9 |
| Likely | title match AND `Total Approvals` ≥ 1 [VERIFY] | 0.6 |
| Possible | has an H-1B record but no title match [VERIFY] | 0.3 |
| Unknown | company not in the CSV, or its H-1B fields are blank | **omitted** (not 0) |
| Avoid | not used; the CSV cannot prove non-sponsorship | — |

- *Unit note:* `Approval_Rate` is stored on a 0–100 scale (observed min 0, max
  100). The decided threshold of 0.90 is applied as **90**.
  Original proposal said 0.90; Claude Code found the column is 0–100 (observed min 0, max 100). Corrected before first commit.
- A **title match** only shows the title appears in
  `top_job_titles_sponsored`. It is not a per-title approval count; approvals
  are per company.
- Possible and Unknown are both in the scorer's "soft tier" list, which demotes
  an Apply to Consider (`role-scorer.mjs:48,99-104`).

**Funding (record, context only):** `latest_funding_*` is shown in the report
but **not scored**. [TODO: DEV] fold funding recency into sponsorship p, per
Ch.7's 0.20 weight (`book/chapters/07-…md:36`).

**Fit (your-input):** the persona rates fit 0–1 after reading the job
description. Fit is required: a missing vote is dropped without
renormalization (`role-scorer.mjs:72-73,80`), so leaving it out would cap the
composite at 0.35 × p.

**Liveness gate (record):** run `npm run ats:liveness` on each URL and record
the result in the input file. Mapping: active → 1.0, uncertain → 0.5, expired →
0.0 [VERIFY]. [TODO: DEV] automate the call. An uncertain posting (0.5) reaches

**Timeline gate (your-input):**
- `remaining_days = 90 − unemployment_days_used` (your-input, from the persona
  profile)
- `deadline = min(today + remaining_days, OPT end date if known)`
- `expected_start = today + hiring_lag_weeks × 7`, where `hiring_lag_weeks` is
  set **per role** in the input file (your-input), default **12** if omitted
  (from Ch.10's Role C example, `book/chapters/10-…md:77`)
- factor = **1.0** if `expected_start ≤ deadline − 30 days`; **0** if
  `expected_start > deadline`; **linear** in between, i.e.
  `(deadline − expected_start) / 30` [VERIFY]

Ch.10 has no formula (`:30,65`), so this was a [TODO: DEFINE], resolved by this
proposal.

*Original rule (OPT start + 90 days) was wrong: the 90 unemployment days are
cumulative. Corrected before first commit after Claude Code showed it zeroed
every role for Priya.*

**Worked example, Priya Nair** (`search/examples/priya-nair/profile.yml`;
today = 2026-10-02):

| Quantity | Value | Source |
|---|---|---|
| Unemployment days used | 34 | `profile.yml:22` |
| Ceiling | 90 | `profile.yml:23` |
| Remaining days | 90 − 34 = **56** | computed; matches the profile's own note, `profile.yml:26` |
| today + remaining | 2026-10-02 + 56 = 2026-11-27 | computed |
| OPT end date | 2027-01-31 | `profile.yml:21` |
| **Deadline** | min(2026-11-27, 2027-01-31) = **2026-11-27** | computed |
| Full-credit cutoff (deadline − 30) | 2026-10-28 | computed |
| Expected start at 12-week lag | 2026-10-02 + 84 = **2026-12-25** | computed |
| **Factor at 12 weeks** | 2026-12-25 > 2026-11-27 → **0** | rule above |

With the default 12-week lag, **every role fails the timeline gate for Priya.**
This is a real finding, not a bug: she has 56 unemployment days left, and a
12-week hiring process takes 84. Under this rule, a role only scores above 0 if
its lag is ≤ 56 days (8 weeks). It gets full credit only at ≤ 26 days (about
3.7 weeks). A 6-week lag gives (2026-11-27 − 2026-11-13) / 30 = 0.467, which
the scorer treats as a soft timeline (< 0.6, `role-scorer.mjs:101`).

[VERIFY] Assumptions the profile does not state outright:
- The rule assumes Priya is unemployed from today, so the clock runs every day.
  The profile gives days used, but not whether she is currently employed. Only
  its note implies the clock is running (`profile.yml:26`).
- The rule hard-codes 90. The profile also says `stem_eligible: true`
  (`profile.yml:25`), and Ch.10 says STEM OPT raises the ceiling to 150
  (`10-…md:21`), but her profile ceiling is 90 and she is on year-1 OPT. The
  rule should read `unemployment_ceiling` from the profile, not a constant.
- The profile's `buffer_target: 20` (`profile.yml:24`) is not used; this rule
  uses a fixed 30-day margin.

## 5. Gates

| Gate | Testable condition | What a human must see to clear it |
|---|---|---|
| Liveness | Every role has `liveness.factor` ∈ {1.0, 0.5, 0.0}, taken from a logged `ats:liveness` run on that exact URL | The command output per URL (result + reason + date) next to the factor recorded in the input file |
| Timeline | Every role has `timeline.factor` ∈ [0, 1], plus the dates that produced it | Days used, remaining days, OPT end date, today, deadline, per-role hiring lag, expected start. Checked against the persona's profile, with every 0 listed as a drop |

## 7. Predictions: what the first pass will get wrong

- **Company-name mismatch:** a typed name ("Affinity Solutions") will not match
  the CSV ("AFFINITY SOLUTIONS INC"), so a real sponsor shows as Unknown.
- **Substring title false positives:** "business analyst" matches "Business
  Analyst Manager - Data Distribution Team" (that string occurs in the CSV).

**Prediction from my own data checks** *(I ran the grep and CSV checks on Wayfair and Deloitte myself; Claude helped me word the conclusion; I reviewed it):*

The prototype will misjudge large employers. Wayfair, a big Boston employer of data analysts, isn't in the CSV at all, so it can only ever come out Unknown. Deloitte appears as 7 separate legal entities with very different records: Deloitte Consulting has 8,810 approvals while Deloitte Financial Advisory is blank, so the result depends entirely on which name gets typed. Also, Deloitte Consulting's top sponsored titles are generic ("Manager", "Senior Consultant"), so my title-match rule would rate one of the largest sponsors in the file as only Possible (p 0.3). I expect title matching to under-rate big consulting firms, where data analysts are often titled "Consultant".

**Design revisions:**
1. **Liveness provenance.** A liveness value is labeled `record` only when it
   is backed by a saved `ats:liveness` output file (`evidence_path` exists).
   Typed fixture values are labeled `your-input (fixture)`. (§3 had labeled
   liveness `record` unconditionally.)
2. **Title match with 0 approvals** raises an error ("row fits no tier rule")
   instead of getting a tier. 0 rows in the real CSV hit this case.
3. **Unemployment ceiling** is now read from the profile
   (`visa.unemployment_ceiling`), not hard-coded as 90. For Priya the result
   is the same: ceiling 90, 56 days remaining, deadline 2026-11-27.
4. **Other input rules.** `opt_end_date: null` means "not known": the deadline
   then uses remaining days only. Hiring lag must be whole weeks, because date
   arithmetic silently drops part-days.
