# 01 — Repository findings (read-only survey)

## Executive summary

These are working notes from a read-only survey of the repository, done before
designing a new recipe. The recipe ranks data/analytics job openings for an
international student on post-graduation work authorization. It uses employers'
past visa-sponsorship records, with the work-authorization clock acting as a
hard stop. Read this before writing the recipe or prototype: it records what the
existing scoring engine will and won't accept, and the rules the submission must
follow to pass automated checks.

Main findings:
- The engine takes three weighted signals (sponsorship, fit, role quality) and
  two hard stops (posting is live, timeline fits). It has no slot for funding
  and does not re-balance weights when a signal is left out.
- No stored rule turns sponsorship records into a probability or a tier, and
  none turns dates into a timeline value. The book describes both only loosely,
  so the recipe has to propose and justify those rules.
- The engine's check for "does this person need sponsorship" disagrees with the
  example persona files. It ignores their explicit yes/no field, so the
  prototype has to supply the profile in the exact shape the code reads.
- The live-posting checker needs a browser and the network. Its classifier
  function can be called offline on saved page content.

## a. Scorer input schema (`scripts/score/role-scorer.mjs`)

Input: a JSON array of role records, or `{roles:[…]}` (`:167-168`). Optional
`--profile p.json`, parsed with `JSON.parse`, so YAML is not accepted (`:163`).

| Field | Kind | Shape | Default source label | Weight |
|---|---|---|---|---|
| `sponsorship` | vote | `{p, tier, source}` | `record` (`:76`) | **0.35** (`:35`) |
| `fit` | vote | `{p, source}` | `model-judgment` (`:77`) | **0.30** (`:36`) |
| `role_quality` | vote | `{p, source}` | `record` (`:78`) | **0.0**, [VERIFY], unpinned (`:37-42`) |
| `liveness` | **gate** | `{factor, source}` | `record`; set to 1 if absent (`:83,86`) | multiplier |
| `timeline` | **gate** | `{factor, source}` | `your-input`; set to 1 if absent (`:84,87`) | multiplier |
| `override` | human | `{decision, reason}` | ignored without a reason (`:115-120`) | — |
| `role_id`, `company`, `title` | labels | — | — | — |

- Composite = `(Σ p·w) × liveness × timeline`. Apply if ≥ 0.30, Consider if
  ≥ 0.20 (that floor is [VERIFY]), otherwise Skip. Any gate ≤ 0.05 forces
  Skip (`:44-46, 93-112`).
- An Apply is demoted to Consider if the sponsorship tier is `likely`,
  `possible` or `unknown` (`:48`), or if timeline < 0.6 (`:99-104`).
- A missing `p` is dropped, not set to zero (`:72-73`). See Follow-up 3:
  weights are not renormalized.
- **No funding term.** Only those three vote keys are read (`:76-78`); a
  `funding` field would be ignored without a warning.
- Profile trap: `applyProfile` (`:56-63`) sets the sponsorship weight to 0 if
  `profile.authorization` matches
  `/citizen|permanent|green|gc|pr\b|no.?sponsor|authorized/`. See Follow-up 4.
- Outputs always go to `<out-dir>/role-scores.json` and `.md` (`:165,175`), so
  each run overwrites the last one in the same directory.

### 1. Timeline gate rule (Ch.10)

Source: `book/chapters/10-the-visa-timeline-manager.md`.

**There is no closed-form formula.** The chapter defines the factor only by
interface and three cases:

- Range and role: "a **timeline factor between 0 and 1** that gets multiplied
  into a role's composite score" (`:30`).
- Inputs (`:36`): "your visa type, your authorization end date, how many
  unemployment days you have already used, whether you are STEM-eligible, your
  field, your target buffer, and the estimated process length for the role
  being scored". (It says "eight intake questions" but lists seven.)
- The "conceptual" signature (`:41-49`), quoted:

  ```
  factor = timeline_factor(
      auth_type              = "OPT",
      auth_end_date          = "2026-08-30",
      unemployment_days_used = 22,
      expected_time_to_start = "16 weeks",
      stem_eligible          = True,
      buffer_target          = "80 days"
  # returns a value in [0, 1]; 0 = skip regardless
  ```

- The three cases (`:65`): factor **0** when "the expected time-to-start
  exceeds your remaining authorization"; **near 1** with "comfortable buffer";
  **between 0 and 1** is "buffer-based scaling, where as the expected start
  date creeps toward the cliff, the factor falls". The shape of that scaling
  (linear or otherwise) is not given.
- The output must carry the dates that produced it (`:52`, `:212-213`).
- Legal ceilings, stated as facts: OPT allows 90 cumulative unemployment days
  (`:19`); STEM OPT allows 150 (`:21`).

**No default hiring lag is pinned.** The only lag values are worked-example
illustrations: "16 weeks" (`:45`), and Role A ≈ 5 months → 0, Role B ≈ 6 weeks
→ ≈ 1, Role C ≈ 12 weeks → ≈ 0.6 (`:73-77`). The "80-day buffer" is called "not
a legal threshold, just a planning discipline" (`:71`).

**No implementation exists.** `grep` for `timeline_factor|timelineFactor|hiring.lag|time_to_start`
across `scripts/` returned nothing.

**Implication:** the timeline rule, the hiring-lag default and the 0–1 scaling
must all be proposed as `[TODO: DEFINE]` items with reasoning. The timeline
factor should stay labeled `your-input` (matches `role-scorer.mjs:87`). The 0.6
example sits right on the scorer's `softTimeline < 0.6` threshold
(`role-scorer.mjs:101`).

### 3. Missing votes: renormalized or not?

**Not renormalized.** A vote whose `p` is missing is skipped:

```js
// role-scorer.mjs:72-73
const p = num(obj?.p);
if (p == null) return;
```

and the sum uses the fixed weights as-is:

```js
// role-scorer.mjs:80
const voteSum = votes.reduce((s, v) => s + v.p * v.weight, 0);
```

No line divides by the total weight present. Omitting `fit` therefore removes
its 0.30 entirely. With `role_quality` at 0, the composite becomes
`0.35 · p_sponsorship · liveness · timeline`, capped at 0.35. Reaching Apply
(≥ 0.30) then needs `p · liveness · timeline ≥ 0.857`; Consider (≥ 0.20) needs
≥ 0.571. Omitting fit is allowed, but it is a strong penalty, not a neutral
choice. It has to be stated in the recipe.

### 6. Does `check-liveness.mjs` need network? Offline mode?

- **Yes, it needs network and a browser.** It imports Playwright `chromium`
  (`check-liveness.mjs:17`), launches it headless (`:40`), and calls
  `checkUrlLiveness`. That function does `page.goto(url, …)`
  (`liveness-browser.mjs:54`) and reads the rendered body and apply controls
  (`:60-62`). CLI usage is URLs or `--file urls.txt` only (`:10-12, 30-36`). It
  has no `--offline`, `--fixture` or dry-run flag. Doctor notes Playwright is
  optional and "ats:liveness needs it" (`doctor.mjs:36`).
- **Offline path:** the decision logic is a pure function,
  `classifyLiveness({ status, finalUrl, bodyText, applyControls })`, exported
  from `scripts/ats/liveness-core.mjs:49`. The browser wrapper calls it
  (`liveness-browser.mjs:95`). A fixture harness can import it and feed saved
  `{status, finalUrl, bodyText, applyControls}` records with no network.
- It returns `active` / `expired` / `uncertain`, with a code such as
  `http_gone`, `expired_url`, `expired_body`, `apply_control_visible`,
  `listing_page`, `insufficient_content` or `no_apply_control`
  (`liveness-core.mjs:50-77`). **It does not return a numeric factor.** The
  mapping from result to the scorer's `liveness.factor` (e.g. active → 1,
  expired → 0, uncertain → ?) is not defined anywhere read, so it is another
  `[TODO: DEFINE]`.
